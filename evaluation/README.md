# Оцінювання вимови й нормалізації

`gold.tsv` перевіряє наголоси на регресійних прикладах. Це не випадкова вибірка й не незалежний тест якості. `normalization.tsv` — точний корпус правил для чисел, років, одиниць, дат та ідентифікаторів; перевірка запускається `node scripts/normalization-eval.mjs`.

Scorer зіставляє кожне повторне входження окремо. `TP` зараховується лише за повного
збігу очікуваних і фактичних наголосів; пропущені очікувані позначки дають `FN`, а
додаткові чи неправильні — `FP`. Невідповідність послідовності слів показується
окремо й не підміняється метрикою наголосів. Перевіряйте `dictionaryValidation` у
`report.json`: невалідні рядки зовнішнього словника пропускаються й лишаються
невирішеними замість автоматичного наголошення.

CI запускає `node scripts/eval.mjs --strict`: він вимагає 100% precision, recall не
нижче 96,9% і повного збереження слів. Пороги фіксують поточну відому похибку; їх
можна змінити разом із поясненням, якщо еталонний набір навмисно змінено.

## Як додавати приклади

- Зберігайте мінімальний вхідний текст і очікуваний результат в окремому рядку TSV.
- Додавайте пояснювальний тег (`year`, `unit`, `identifier` тощо), а не виводьте висновки з кількості прикладів.
- Рядки `gold.tsv` та `normalization.tsv` — тестові дані, а не підтвердження повної відповідності нормі. Для двозначної вимови додайте джерело й контекст у `lexicon/` або збережіть варіант як невирішений.
- Не переносіть фрази з робочого сценарію або приватного корпусу у публічний пакет без окремого рішення про їхню публікацію.

## Відкладена вибірка й аудіювання

Незалежний holdout має походити з окремих текстів, не використаних для написання правил. Фіксуйте версію пакета, рушій, точну модель/голос, налаштування, хеш вхідного й вихідного файлів та оцінку слухача. Порівняння аудіо має бути сліпим A/B: слухачеві не показувати, який варіант зроблений новою версією. Не змішуйте оцінки правильної вимови з якістю відеоряду, таймінгом або гучністю.

### Підготовка сліпого A/B

`ua-tts-text-blind-audio` формує локальний пакет слухача й окремий ключ організатора. Зберігай маніфест, джерельні WAV, ключ, відповіді й звіт у `evaluation/private/`; ця тека ігнорується Git. Не клади приватні матеріали до `gold.tsv` чи інших відстежуваних файлів.

Відкладай holdout із незалежних текстів. Для кожного прикладу спочатку заморозь початковий текст, а потім згенеруй обидві версії з однаковими рушієм, голосом і налаштуваннями TTS. Міняй лише версію `ua-tts-text`, інакше порівняння матиме кілька причин зміни.

Створи приватну теку й поклади WAV за відносними шляхами з маніфесту. У наведеному прикладі це `evaluation/private/audio/0.15.0/001.wav` та `evaluation/private/audio/0.16.0/001.wav`. Маніфест `evaluation/private/study.json`:

```json
{
  "format": "ua-tts-blind-audio-study",
  "version": 1,
  "studyId": "holdout-2026-11",
  "engine": "tts-uk",
  "voiceModel": "назва точного голосу або моделі",
  "settings": { "rate": 1 },
  "packageVersions": ["0.15.0", "0.16.0"],
  "samples": [
    {
      "sampleId": "holdout-001",
      "text": "Текст, який було озвучено.",
      "audio": {
        "0.15.0": "audio/0.15.0/001.wav",
        "0.16.0": "audio/0.16.0/001.wav"
      }
    }
  ]
}
```

Усі шляхи до аудіо мають бути відносні до папки маніфесту й не можуть вести за її межі. Приймаються WAV PCM або IEEE-float; перед копіюванням скрипт зберігає `fmt `, `data` та перші чотири байти `fact` (кількість семплів), прибирає інші RIFF chunks і записує SHA-256 початкових та підготовлених файлів у ключі.

Підготуй нову директорію виходу (вона не має вже існувати; її батьківська тека `evaluation/private/` має існувати):

```bash
npx ua-tts-text-blind-audio prepare \
  --manifest evaluation/private/study.json \
  --outdir evaluation/private/blind-study
```

Слухачеві передавай лише `blind-study/participant/`. У ній є текст, знеособлені шляхи A/B і `responses.json`; версії та початкові імена файлів не додаються. Залиш `blind-study/organizer/key.json` приватним. Збалансовані призначення сторін і порядок прикладів перемішуються окремо. Для кількох слухачів створи кожному окремий пакет, щоб їхні відповіді мали незалежний порядок.

Слухач заповнює для кожного прикладу `preferredSide` (`A`, `B` або `tie`), оцінки `stressCorrectness` (наскільки правильно почуто наголоси відносно тексту) і `naturalness` від 1 до 5 для обох сторін, та за бажанням `notes`. Після повернення файлу з відповідями організатор формує звіт:

```bash
npx ua-tts-text-blind-audio score \
  --key evaluation/private/blind-study/organizer/key.json \
  --responses evaluation/private/blind-study/participant/responses.json \
  --out evaluation/private/blind-study/organizer/report.json
```

Звіт зіставляє оцінки з версіями для кожного прикладу, додає хеш маніфесту й підсумовує переваги та середні оцінки. Це описові результати саме цього набору й слухача; інструмент не обчислює статистичну значущість і не перетворює їх на загальну заяву про якість. Поки що в репозиторії немає готових незалежних аудіо-оцінок.
