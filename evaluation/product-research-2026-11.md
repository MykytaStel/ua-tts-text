# Напрями розвитку українського TTS frontend

Перевірено 2026-11-15. Це дослідження першоджерел і пропозиції експериментів, не реалізація та не підтвердження поліпшення звучання. Поточні README upstream можуть змінюватися; перед інтеграцією слід зафіксувати версію/commit. Локальний контекст: `README.md`, `evaluation/README.md`.

## 1. Типізовані фрагменти перед перетворенням на слова

**Підтверджено.** NeMo розділяє класифікацію й вербалізацію: `MoneyFst` спершу створює структурований токен із полями цілої/дробової частини й валюти, інший автомат перетворює його на мовлення. Це конкретний зразок проміжного представлення, а не лише послідовність замін. [Класифікатор](https://github.com/NVIDIA/NeMo-text-processing/blob/main/nemo_text_processing/text_normalization/en/taggers/money.py), [вербалізатор](https://github.com/NVIDIA/NeMo-text-processing/blob/main/nemo_text_processing/text_normalization/en/verbalizers/money.py).

**Пропозиція.** Спершу розпізнавати `date`, `decimal`, `fraction`, `measure`, `money`, `identifier`, `url` зі span вихідного тексту; зберігати сирий запис і значення окремо. Зокрема, `000123` як ідентифікатор не повинен проходити загальне перетворення цілого числа. Після визначення типу формувати граматично припустимі прочитання. Почати можна з TypeScript parser/IR: перенесення архітектури не потребує негайного впровадження WFST.

**Межі.** В актуальному CLI NeMo серед мов немає `uk`; готової української TN цим джерелом не підтверджено. Код — Apache-2.0. Python/Pynini/OpenFst створюють додатковий інтеграційний тягар; README окремо застерігає про pip-інсталяцію на macOS/Windows. [Список мов](https://github.com/NVIDIA/NeMo-text-processing/blob/main/nemo_text_processing/text_normalization/normalize.py), [ліцензія](https://github.com/NVIDIA/NeMo-text-processing/blob/main/LICENSE), [встановлення](https://github.com/NVIDIA/NeMo-text-processing#installation).

## 2. Контекст обирає серед допустимих кандидатів

**Підтверджено.** Bakhturina, Zhang, Ginsburg (2022) описують недетермінований WFST, який генерує кандидати нормалізації, та мовну модель, яка обирає прочитання в контексті. Поточний NeMo hybrid README прямо описує ранжування кандидатів pretrained masked language model. [Стаття](https://arxiv.org/abs/2203.15917), [реалізація/опис](https://github.com/NVIDIA/NeMo-text-processing/blob/main/nemo_text_processing/hybrid/README.md).

**Пропозиція.** Для неоднозначного запису повертати перелік кандидатів з ID; локальна модель або LLM може тільки вибрати ID чи відмовитися. Так можна поширити наявний принцип вибору наголосу на нормалізацію. Зберігати джерело правила, контекст і рішення для review. Кандидати мають бути обмежені значенням початкового токена; рейтинг моделі не може змінювати число чи назву одиниці.

**Межі.** Це адаптація відомої схеми, не новий алгоритм. Якщо генератор пропустив правильний кандидат, ранжування його не відновить. Заявлена авторами якість не доводить якість української реалізації. Потрібно вимірювати окремо наявність правильного кандидата, точність вибору, відмови й семантичні помилки.

## 3. Морфологія для граматичних омографів

**Підтверджено.** `lang-uk/ukrainian-word-stress` використовує Stanza POS/morphology для вибору словникового наголосу; словниковий режим пропускає неоднозначність. Автори відокремлюють граматичні випадки на кшталт різних форм `блохи` від смислових на кшталт `атлас`, які морфологія не розв'язує. Формат словника містить варіанти наголосу та морфологічні/POS теги. [README](https://github.com/lang-uk/ukrainian-word-stress), [формат](https://github.com/lang-uk/ukrainian-word-stress/blob/main/docs/dictionary_format.md).

**Пропозиція.** До частотних/суфіксних здогадок додати окремий морфологічний аналізатор: зіставляти число, відмінок, частину мови та допустимі словникові варіанти. Порівняти поточні правила, upstream Stanza режим і власний constrained resolver на тому самому українському holdout.

**Межі.** README вказує приблизно 500 MB завантажень моделей; це не безкоштовна за ресурсами заміна компактного Node-пакета. Наведена частка однозначних словоформ у словнику не є точністю на реальному тексті. Код позначений MIT; ліцензії конкретних моделей і джерельних даних потрібно перевіряти окремо, MIT репозиторію не доводить їх. [MIT](https://github.com/lang-uk/ukrainian-word-stress/blob/main/LICENSE).

## 5. Piper: справжній канал керування фонемами

**Підтверджено.** Поточна документація OHF Piper описує вставлення сирих espeak-ng фонем блоками `[[ ... ]]`; це більш виразний канал, ніж заміна знака наголосу в звичайному тексті. [CLI, Raw Phonemes](https://github.com/OHF-Voice/piper1-gpl/blob/main/docs/CLI.md#raw-phonemes). Репозиторій позначений GPL-3.0, а ліцензії голосів винесені окремо. [Репозиторій](https://github.com/OHF-Voice/piper1-gpl).

**Пропозиція.** Додати експериментальний адаптер із capability `phonemeInput`, який для перевірених слів передає фонеми та наголос, а для решти лишає звичайний текст. Порівняти «звичайний текст / графічний наголос / фонемний ввід» одним голосом і однаковими параметрами.

**Межі.** Підтверджена можливість актуального upstream, а не встановленої локальної версії. Потрібні сумісні символи phoneme map конкретного голосу, український G2P і аудіоперевірка. Документація вводу не доводить правильної української вимови. Старі Piper binaries не слід автоматично вважати сумісними з поточним Python API.

## 6. Azure: можливості треба прив'язувати до конкретного API

**Підтверджено.** Microsoft документує SSML `phoneme`, `sub`, custom lexicon, залежні від locale набори фонем і HTTP 400 для невідомих фонем. [Pronunciation SSML](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/speech-synthesis-markup-pronunciation). Поточна таблиця має `uk-UA-PolinaNeural` та `uk-UA-OstapNeural`; вони не позначені приміткою 3 про відсутність phoneme/custom lexicon. Однак окрема таблиця **Video translation** для `uk-UA` вказує `TTS custom lexicon phoneme target: No`. [Language support](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/language-support?tabs=tts).

**Висновок з документації.** Не можна переносити можливості стандартного Azure TTS на Video translation, Edge TTS чи інші шлюзи. Водночас не слід категорично стверджувати, що Azure взагалі не має каналу керування українською вимовою: таблиця стандартних голосів цього не показує.

**Межі та наступна перевірка.** На відкритій сторінці phonetic sets українського набору не знайдено. Тому працездатну українську IPA-таблицю й конкретний SSML payload цим дослідженням не підтверджено. Для статусу «підтримано» потрібен реальний запит до конкретного голосу й слухова перевірка мінімальних пар; до цього позначати capability як неперевірену. [Phonetic sets](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/speech-ssml-phonetic-sets).

## Обмежений перший експеримент

Пропозиція для обговорення: заморозити незалежні 100–200 фраз із датами, дробами, одиницями, кодами й граматичними омографами; порівняти поточний результат із типізованим розбором та обмеженим вибором кандидатів. Це рекомендований дизайн експерименту, а не вже виконаний benchmark.

### P0: перетворення може змінювати значення

Фактичні результати `normalize(input)` із типовими параметрами:

| Вхід | Фактичний вихід |
|---|---|
| `Зустріч о 12:30.` | `Зустріч о дванадцять, тридцять.` |
| `Рахунок матчу 2:1.` | `Рахунок матчу два, один.` |
| `Додайте 1/2 склянки води.` | `Додайте один на два склянки води.` |
| `Дата: 2026-11-15.` | `Дата, від двох тисяч двадцяти шести до одинадцяти-п'ятнадцять.` |
| `Код товару 000123.` | `Код товару сто двадцять три.` |
| `До 1,5 км.` | `До одна ціла п'ять десятих кілометра.` |
| `Швидкість 90 км/год.` | `Швидкість дев'яносто кілометрів/год.` |
| `Площа 20 м².` | `Площа двадцять метрів².` |
| `Температура −5 °C.` | `Температура −п'ять градусів.` |
| `Ціна $25 та 25 €.` | `Ціна $двадцять п'ять та двадцять п'ять €.` |

Контрольні випадки працюють: `У 2026 році.` → `У дві тисячі двадцять шостому році.`; `Доставка за 1 000 000 грн.` → `Доставка за один мільйон гривень.`. Проблема не в кожному числі, а в визначенні типу, перекритті правил та граматичному контексті. Нерозгорнута одиниця й тихо змінене значення — різні класи дефектів, їх слід рахувати окремо.

Причини у [normalize.ts](../src/normalize.ts): `expandRatios` трактує кожен відповідний `a/b` як співвідношення; ISO-дата не захищена перед розбором діапазонів; загальний числовий прохід втрачає початкові нулі; одиниці розбираються без повної структури складеної одиниці. Послідовність regex працює над уже зміненим рядком без типізованого представлення початкових фактів.

### P0: readiness gate не перевіряє збереження значення

`prepare` з `piper-medium`, наявним словником та `stress.trace: true` повертає:

| Вхід | Результат `checkPrepared` | Спостереження |
|---|---|---|
| `Код товару 000123.` | `passed: true`, `findings: []` | Нулі втрачено, залишилося «сто двадцять три». |
| `Дата: 2026-11-15.` | `passed: true`, `findings: []` | Дата перетворена на діапазон; також `inferred: 1`. |

[checkPrepared](../src/index.ts) перевіряє lint кінцевого тексту, невідомі слова, неоднозначності й вибрані попередження ресурсів. Початкові значення та ризик здогаданого наголосу не входять у цей контракт. Наявне `passed` означає відсутність цих конкретних findings, а не правильність вимови чи незмінність змісту.

Мінімальне відтворення після збірки й завантаження словника:

```js
import path from 'node:path';
import { normalize, loadResources, prepare, checkPrepared } from './dist/index.js';

const resources = loadResources({
  home: '/private/tmp/ua-tts-product-audit-empty-home',
  dictionaryPath: path.resolve('data/dict.bin'),
  required: true,
});
for (const input of ['Код товару 000123.', 'Дата: 2026-11-15.']) {
  const result = prepare(input, {
    resources,
    engine: 'piper-medium',
    stress: { trace: true, minReportLength: 1 },
  });
  console.log({ input, normalized: normalize(input), text: result.text, check: checkPrepared(result) });
}
```

### P1: статистичні здогадки наголосу потребують окремої оцінки

[dict.ts](../src/dict.ts) у `stemStress` голосує позиціями наголосу перших максимум 12 словникових записів із відповідним префіксом. Це евристика за формою слова; вона не встановлює спільну лему, частину мови чи акцентну парадигму. Суфіксний fallback використовує останні п'ять літер і поріг частоти; ця частота не є каліброваною ймовірністю правильності на нових текстах. Автоматично виведений наголос має evidence, але readiness gate його не оцінює.

`unknownPrompt` у [resolve.ts](../src/resolve.ts) надсилає лише слова й просить позицію голосної. Контекст речення відсутній, результат прив'язаний до слова глобально. Для омографів уже є рішення по входженнях; цю властивість варто поширити на невідомі слова й нормалізацію.

У README наведено 98% для stem fallback і приблизно 87% сумарної точності невідомих слів. Відтворюваного split/звіту, який підтверджує саме ці цифри, у перевірених поточних evaluation scripts не знайдено. Це обмеження відтворюваності, а не доказ, що експеримент ніколи не проводився.

### P1: тести ще не вимірюють виграш для користувача

- Поточний normalization evaluation має 13 прикладів.
- Збережений `evaluation/report.json` має 28 рядків, 128 TP, 0 FP, 4 FN та resource version 0.17.0. Сам звіт правильно називає це regression corpus, не незалежною оцінкою.
- `evaluation/README.md` прямо повідомляє про відсутність готових незалежних аудіооцінок.
- README відстає від коду: CLI 0.18 позначений у роботі, хоча package version уже 0.19.0. Публічний npm dist-tag в цьому аудиті не перевірявся.
- Частка слів із поставленим наголосом не доводить, що наголос правильний або що голос його відтворює.

Потрібні окремі результати для «оригінальний текст → голос», «0.19 → той самий голос», «експеримент → той самий голос». Головні метрики: спотворення числа/дати/одиниці; правильність наголосів при явно вказаному покритті й частці відмов; ручні виправлення на 1000 слів; сліпа оцінка звучання; затримка й пам'ять. ASR-транскрипція може допомогти знайти пропуски чи підміни слів, але не замінює слухову перевірку наголосів.

### P1: спільна структура потрібна також для Studio й планування

`normalizeWithTrace('5 км і 5 км.').steps` повертає дві однакові події `before: '5 км'`, `after: "п'ять кілометрів"` без позицій початкового тексту. Це пояснення правила, але недостатня карта для прив'язування редакторського виправлення до конкретного входження. Потрібне відображення початкових і озвучуваних фрагментів, включно з перетвореннями «один до багатьох».

`planSpeech('Д-р Іваненко прийде о 12:30. Ціна 1,5 грн.')` розбиває час між `12:` і `30.`, а десяткове число між `1,` і `5 грн.`. Планування пауз має використовувати ті самі захищені типізовані фрагменти.

[render.ts](../src/render.ts) здебільшого задає формат позначки наголосу. Повноцінна підтримка рушія потребує перевіреної комбінації версії, голосу, API та каналу вимови. Прямий ввід фонем Piper із розділу 5 — експеримент для такої перевірки; поточне категоричне твердження «виправити наголос текстом неможливо» не описує всі можливості актуального upstream. Успішний вибір наголосу всередині пакета й фактична передача цього вибору голосу повинні мати різні статуси.

### P2: простота інтеграції

Пакет має корисні основи: локальний словник, проєктні overrides, рішення по входженнях, fingerprint ресурсів і trace. Їх варто зберегти. Водночас є лише кореневий export із Node imports; окремого browser-safe entry point для чистої нормалізації немає. Доцільний напрям після виправлення семантики: легке чисте ядро + окремі Node ресурси + опційний NLP backend. Браузерний bundle в цьому аудиті не будувався.

## Пропонований продуктовий фокус

Перший цільовий сценарій — редактор української озвучки у Studio: автор бачить оригінал, система готує мовлення, показує конкретні ризикові місця, зберігає підтверджені виправлення для наступних текстів. Пакет відповідає за лінгвістичні правила й структуру; Studio — за інтерфейс і синтез. Це дозволяє уникнути дублювання правил у споживачах. Потребу ширшого ринку слід перевіряти також на незалежних інтеграціях; цей аудит її не вимірював.

Пропонований результат аналізу має тримати окремо оригінал, типізовані фрагменти зі значеннями та позиціями, кандидати прочитання, рішення з джерелом, відображення в spoken text і список невирішених питань. Приклад: `000123` як identifier зберігає всі символи; спосіб групування цифр залежить від політики проєкту. Сумнівний запис не має потрапляти в загальний numeric fallback без явного рішення.

Перспективні експерименти:

1. **Типізований parser + обмежений вибір кандидатів.** Порівняти послідовні regex із parser/IR для часу, дат, дробів, діапазонів, кодів, грошей і складених одиниць. Правила генерують допустимі прочитання, контекст вибирає; при невизначеності система повертає питання для review. Незалежні еталонні приклади перевіряють число, знак, дату, одиницю й збережені цифри коду. Зворотний parser може бути додатковим сигналом, але спільна помилка двох parser не є доказом правильності.
2. **Морфологія + компактна модель наголосу.** Порівняти поточний fallback, граматичне звуження кандидатів та невелику символьну модель на однакових splits за лемами/сім'ями. Складну модель включати опційно лише після виміряного виграшу. Окремо навчати або калібрувати відмову від рішення; не прирівнювати максимальний score до достовірності.
3. **Адаптер фонем для одного голосу.** Зафіксувати Piper version/voice; порівняти звичайний текст, графічний наголос і прямі фонеми на мінімальних парах. Приймати адаптер після прослуховування, а не лише валідного WAV.
4. **Підтверджені редакторські виправлення.** Зберігати слово/входження, контекст, правильне прочитання, джерело та scope проєкту. Використовувати для доменних пакетів власних назв, брендів і скорочень. Відповіді LLM не стають еталоном без перевірки; приватні тексти не публікуються автоматично.

## Послідовність робіт і критерії приймання

| Етап | Результат | Критерій приймання |
|---|---|---|
| 0.20: збереження змісту | Типи date/time/fraction/identifier/measure, захист перекриттів, semantic findings, позиції вихідних фрагментів, узгоджений planSpeech | Відомі спотворення з цього аудиту усунуті; неоднозначні випадки явно нерозв'язані; нуль спотворень на погодженому acceptance corpus, із зазначенням його розміру та меж |
| Наступний етап: контекстний наголос | Граматика, контекст для unknown по входженнях, виміряний fallback і відмови | На незалежних лемах/документах кращий баланс точності й покриття, менше редакторських виправлень, виміряні ресурси |
| Наступний етап: вимова та інтеграції | Перевірений адаптер конкретного голосу, карта original → spoken, корекції зі Studio | Сліпий аудіотест проти оригінального TTS та попередньої версії; виправлення застосовується до потрібного входження й переживає повторний запуск |
| 1.0 | Стабільний контракт підтримуваних випадків, формати даних, відтворювані метрики й інструкція інтеграції | Реальний виграш у цільових сценаріях на незалежному матеріалі; документовані межі замість універсальних обіцянок |

Номери після 0.20 навмисно не призначені наперед: експеримент може не покращити результат. Незалежні 100–200 фраз треба відокремити від наведених діагностичних прикладів; відомі дефекти стають development/regression набором. Після підгонки правил під тест він уже не є незалежним. Пропоновані критерії — цілі майбутньої роботи, не досягнуті результати цього аудиту.
